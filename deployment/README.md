# Dexter deployment gate

This gate is designed for public GitHub repositories whose trusted `main` branch contains a Python backend and Vite frontend like MacroLens. Every five minutes Dexter checks the GitHub API for the current `main` commit and the latest matching `ci.yml` push run. Only a completed successful run from the same repository is eligible. It checks again after the build, before switching. Pull requests, forks, pending or failed CI, and superseded commits are ineligible. GitHub Actions receives no deployment credentials. API outages or rate limiting leave the current release running.

Each release is built under an unprivileged per-app account, with a separate SQLite test database and test-only signing key. The gate clones the approved revision, installs dependencies, runs backend and frontend tests, builds the frontend, and preserves prior hashed assets for existing browser tabs. The root-owned switch helper updates a symlink and systemd drop-in, restarts the existing service, and checks its local health endpoint. If the switch fails it restores the previous symlink and service configuration. The release directory name identifies the deployed commit; inspect the timer/service journal for failures.

## Onboarding another app

These steps require a Dexter administrator and are intentionally explicit: use a separate account, service, storage, and tunnel or route for each app. Do not reuse another app's production credentials. The helpers support this specific backend/frontend layout; a different stack needs an explicitly reviewed builder and switch configuration before use.

1. Create a public repository with `.github/workflows/ci.yml` running on `push` to `main`, including the appropriate tests and build. Protect `main` and restrict who can push or change the workflow: trusted main-branch code runs on Dexter with the app service's privileges. Forks and pull requests must not receive secrets. GitHub-hosted CI may execute PR code if separately configured, but this gate never deploys PR events.
2. Create the application service with its own persistent data and environment file, and verify `GET /api/health` returns `{"status":"ok"}` on a loopback-only port. This helper assumes `backend/deploy_app.py`, `frontend/dist`, and an `uvicorn` service. Ensure persistent paths are absolute and writable through any systemd sandbox. Back up data before enabling schema migrations; rolling back application code does not reverse database migrations.
3. Install the reviewed `gate.py` and `switch.py` as root-owned, non-writable `/usr/local/lib/hackerpod-deploy/gate.py` and `/usr/local/sbin/hackerpod-deploy-switch`, and install `uv` at `/usr/local/lib/hackerpod-deploy/uv`. Install Node 24 and npm at `/opt/node-v24.21.0-linux-x64/bin`. Updates to these root-owned helpers require administrator review; repository pushes do not update them automatically.
4. Create a dedicated non-login deployment account and its writable `/srv/hackerpod/APP` directory. Create root-owned `/etc/hackerpod-deploy/apps/APP.json` containing `{"repository":"OWNER/REPO","service":"APP.service","port":PORT}`. APP must start with a lowercase letter and contain only lowercase letters, digits, or hyphens. Grant that account sudo access only to `/usr/local/sbin/hackerpod-deploy-switch APP *` in a validated root-owned sudoers file. The helper validates argument count and the commit ID; do not give the account broader sudo access.
5. Install a oneshot systemd service running `/usr/bin/python3 /usr/local/lib/hackerpod-deploy/gate.py APP` as the deployment account, with `HOME` set to its home and a timer with `OnBootSec=2min`, `OnUnitInactiveSec=5min`, and `Persistent=true`. Enable the timer and inspect its journal. On first migration, copy only the existing public frontend's hashed assets into `/srv/hackerpod/APP/legacy-assets`, readable by the deployment account, to support already-open tabs. The gate carries these assets forward.
6. Configure the desired `*.hackerpod.dev` DNS and a dedicated Cloudflare tunnel route to the app's loopback port using the existing Cloudflare administration process. Keep tunnel tokens outside the repository. Verify the public endpoint, the local health endpoint, and an actual successful CI-triggered deployment. Never expose the local backend port directly to the internet.

## Operations

`readlink /srv/hackerpod/APP/current` shows the active commit. Use `systemctl status hackerpod-deploy-APP.timer` and `journalctl -u hackerpod-deploy-APP.service` to diagnose. An administrator can disable the timer and restore a previous release with `/usr/local/sbin/hackerpod-deploy-switch APP COMMIT`; health checking and rollback still apply. Re-enable the timer only after deciding whether current main should redeploy. Do not delete the original service configuration, database, secrets, or tunnel when removing a release.
